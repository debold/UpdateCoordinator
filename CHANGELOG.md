# Changelog

All notable changes are documented here. Format based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Agent and central server are versioned separately ([Semantic Versioning](https://semver.org/), git tags `agent/vX.Y.Z` and `server/vX.Y.Z`).

## [Unreleased]

### Both

- Maintenance windows can be limited to weeks of the month ("only in" the 1st–4th or last week, or "all except" some of them), for monthly windows such as the second Tuesday or every Saturday except the last.
- Renamed from the working title UpdateCoordinator to **SUSyphos**: namespaces, projects, packages (`SUSyphos.Agent.msi`, `SUSyphos.Server.msi`), services, registry keys (`HKLM\SOFTWARE\SUSyphos\…`, policy key `HKLM\SOFTWARE\Policies\SUSyphos\Agent`), data folders (`%ProgramData%\SUSyphos`), webhook header (`X-SUSyphos-Signature`). Installations of UpdateCoordinator (up to 0.4.0) are not upgraded: uninstall them and install SUSyphos anew. The protected files and the trust binding use new purpose strings.

### Agent

- Moves to a new central server when the current one announces its address: it switches only if the server there proves the same trust anchor and accepts its credentials, then writes `CentralServerUrl` and restarts its service; otherwise it stays and reports why with the heartbeat (tried again every 15 minutes, never when group policy sets the address).
- Applies central agent settings delivered with the release list at run time (heartbeat, search and inventory intervals, back-off, log level and files, memory limit, priority, minimum free disk space, drivers in the search, restart warning time and message) and keeps them in a protected file for the next start; registry and policy values still win. Log level and priority changes restart the service.
- The inventory reports whether the Microsoft Update service is registered, so the dashboard shows the real update source.
- Looks up the released updates a search did not find and reports those Windows Update no longer knows at all (`notOffered`), so the central server can spot updates Microsoft withdrew.
- New remote actions "uninstall, restart right after" and "uninstall, restart in the next maintenance window": removes the named update through Windows Update, or with DISM by its KB number where Windows Update cannot (e.g. combined servicing stack and cumulative packages); the local veto prevents only the restart.
- Self-update: msiexec failed with exit code 1619 (sharing violation, log note 2203 with 0x80030020) because the agent kept the verified package open with write access. The package is now verified and installed through a read-only handle that still keeps others from changing it. Agents up to 0.7.2 have the error and cannot update themselves: install a fixed version on them once by hand (or by software distribution); from then on remote updates work.
- New remote actions "install now, restart right after" and "install now, restart in the next maintenance window": install every released update the server misses at once, outside the window and before its time (pause and leases apply, the local veto prevents only the restart).
- Reports with every available update the updates it supersedes (Windows Update `SupersededUpdateIDs`).
- Installs releases marked `outsideWindows` (updates that never restart, e.g. definition updates) also outside the maintenance windows; pause, health check and leases still apply, reboots still wait for a window.
- A failed self-update is forgotten once the agent runs the target version or a newer one (e.g. after a manual installation), so the central server no longer lists it.
- The heartbeat reports when the next update search and the next inventory are due.
- Microsoft Update on request of the central server: the agent registers the service and searches, inventories and installs through it, so other Microsoft products are covered; it removes only its own registration again.
- The update search also finds drivers: everything Windows Update offers is reported and can be released.
- New remote actions "restart in the next maintenance window" (held until a window is open long enough, regardless of the reboot policy, local veto still applies; planned time reported with the heartbeat) and "cancel restart" (also aborts an announced restart).
- The log no longer records four lines per heartbeat: HTTP client messages (`System.Net.Http.HttpClient`) are logged from level Warning (also on the central server).
- The inventory carries the Windows Update history of the last 90 days with the application that started each operation, so installations outside SUSyphos (Automatic Updates, Settings, Defender, wusa) become visible.
- Live status: search, download, installation and inventory are reported to the central server while they run, with progress in percent for download and installation (asynchronous WUA jobs; falls back to the synchronous calls if Windows refuses them). The heartbeat also tells why a pending reboot waits (policy "Never", local veto, pause, outside the window, window ends soon, recently requested, waiting for a lease) or that the agent is restarting the server.
- Registers once at the central server and stores client GUID and client secret encrypted with DPAPI under `%ProgramData%\SUSyphos\Agent`.
- Sends a heartbeat every 10 seconds (configurable) and logs changes of the registration state.
- Resource limits: runs with below-normal process priority and restarts its service when private memory stays above 200 MB after a full garbage collection (`Resources:*`).
- Log upload measures the compressed size of each file first and packs the archive only once (before: up to about 370 MB memory for 80 MB of poorly compressible logs, now about 70 MB).
- Registers again automatically if the central server no longer accepts its credentials.
- Backs off exponentially (up to 5 minutes, configurable) while the central server is unreachable; timeouts and circuit breaker via `Microsoft.Extensions.Http.Resilience`. No error stops the service.
- Accepts only HTTPS addresses for the central server and validates every server response.
- Reads the central server address from the registry value `CentralServerUrl`; the group policy key overrides the installer key and all other configuration sources.
- Trust anchor: pins the anchor of the central server on first contact and accepts only the TLS certificate bound to it by a signed binding with increasing serial, independent of CA and host name. Sends nothing to an untrusted central server.
- Local trust reset via registry value `TrustResetToken` (once per change), logged and reported to the central server.
- An inconsistent stored trust state is treated as first contact instead of stopping the service.
- Inventory: OS (product, edition, display version, version with UBR), domain, roles, update source (WSUS reported as warning) and installed updates via the WUA API (local cache only, COM objects released explicitly). Collected every 6 hours (configurable), sent on start, on change and at least daily.
- Role detection by rules: built-in rules for domain controller, Exchange, SQL Server, cluster node and Hyper-V; additional rules via `Inventory:RoleRules` without code changes.
- Heartbeat carries the current OS version including UBR.
- Update run on approved agents every 4 hours (configurable): pre-flight checks (disk space, Windows Update service, WSUS warning), online search for available updates via the WUA API and report to the central server; search failures are reported with their error code.
- Fetches the released updates when the release version announced in the heartbeat changes.
- Installation of released updates inside maintenance windows (default Mon–Fri 19:00–05:00, Sat/Sun all day, configurable): batches with pull-forward tolerance, no retry loop (retry delay), health check first, global pause respected, one WUA download/install cycle per batch. Reboots only when the central policy allows it (see below); otherwise a needed reboot is reported.
- Install reports are buffered on disk and delivered when the central server is reachable again.
- Uses the maintenance windows delivered by the central server; local `Installation:Windows` is only the fallback. Invalid central windows are rejected.
- Reboots inside the maintenance window when the central reboot policy allows it: pending reboot detected from Windows (also after updates installed by others), at least 30 minutes left in the window, 5-minute warning via shutdown.exe, at most one request per 6 hours, never during a global pause; local veto via registry value `AllowReboot` (only 1/true allows). Heartbeat reports pending reboot and last boot time.
- Runs remote actions announced in the heartbeat and confirms each one; unknown actions are rejected. Reports its Windows time zone with the inventory.
- In coordinated groups installs and reboots only with a lease; keeps it across its own restart and releases it with the outcome.
- Reports its host name with every heartbeat (clone detection).
- Reads the Windows Automatic Updates setting (group policy, then local setting: mode, scheduled restart, compliance deadline) and reports it with the inventory and as pre-flight check `AutomaticUpdates`; a warning when Windows installs or restarts on its own and so bypasses rings and maintenance windows. On central opt-in it sets "Configure Automatic Updates" to option 3 where no group policy controls it, and removes only its own value again when switched off.
- Updates itself to the agent version the central server releases for its ring: downloads the package from the central server into a folder only SYSTEM and administrators can access, checks size and SHA-256, runs msiexec silently and reports failures with the heartbeat (retried after 6 hours, `AgentUpdate:*`).
- Trusts only the central server whose trust anchor matches the fingerprint from the installer file name, when one was given (no trust on first use for downloaded installers).
- Installer: reads central server address and anchor fingerprint from its own file name when downloaded from the central server (also with a browser suffix such as " (1)"); the interactive setup asks for the address, pre-filled from command line, file name or installed value, and checks it.

### Central server

- **Move to a new server** (Backup page): announce the address of a central server restored from this server's backup; agents switch after checking the trust anchor, the box counts the servers still reporting here and lists those that could not move with the reason (also on the server page).
- **Agent settings** (Administration → Agent settings): central defaults for all agents, overrides per server group and per server in collapsed sections that show the applied value and where it comes from.
- Windows Automatic Updates and Microsoft Update can be set per server ("Inherit from groups or system" by default). The System box shows the update source the agent reports, with a "set: …" tag while it differs from the setting.
- TLS certificate page lists every certificate in the store; unusable ones are marked "Not usable" with the reason (expired, no private key, key not accessible, no server authentication).
- Server list: a mark next to the agent version (current, update available, update failed), a donut with the pending updates instead of a number, a dot before the last heartbeat (within 5 minutes, within an hour, older) and a "select all" box in the table header (also on the update and approval lists).
- Update list: superseded and completed updates are hidden unless "Show superseded" or "Show completed" is ticked; the Missing column is gone (the donut tooltip has the count). A superseded update links the update that replaces it ("KB… (Version …)") here and on the update page; start rules no longer start updates that a known newer update replaces.
- Ring page: waiting updates are marked "Superseded" or "Stopped" and hidden unless superseded ones are shown; the title of an update opens its update page and "per server ›" opens the per-server tab.
- Assignment rules link their ring or group to the filtered server list and have a "Servers" column with the number of matching servers (opens the server list filtered by the rule).
- Feedback and success cells say "no server needs it" instead of percentages when no server in the ring misses the update.
- Server page: the tasks show a running search or inventory as "now" and hide the planned window installation while installing or while "install now" is queued; no extra note in the action band after starting an action. The "No restart" option is named the same in the error message and the dialog.
- Messages after an action appear as a toast when the page keeps its scroll position, so they are always in view.
- Identity: AD group, role and "Add" in one row; picking a privileged group (e.g. Domain Admins) warns right at the field, and mapped privileged groups carry the tag "usually gives no role (UAC)".
- Updates withdrawn by Microsoft: when servers report that Windows Update no longer knows a released update, no server still gets it offered and no newer revision or superseding update explains it, the update is marked "Withdrawn by Microsoft", its rollout stops at once and a notification is sent; Release rules → "Updates withdrawn by Microsoft" can switch to notifications only.
- **Block** on the update page (Operator): stops the rollout and keeps start rules and operators from starting the update again until it is unblocked. **Block and uninstall…** (Admin) also lets every server that has the update uninstall it, and **Uninstall update…** on the server page removes one update from one server, each with the restart right after or in the next maintenance window.
- The help showed a garbled character instead of "…" in two places (update list and update page).
- Icons (Lucide, ISC license) before every entry of the navigation and, larger, before the page title: inline SVG from `assets/icons/lucide`, no extra requests or scripts. Navigation renamed: Users is now **Identity** (local accounts and AD groups), Groups is now **Server groups**; the time zone line is gone from the navigation (all times stay in the time zone of the central server).
- Superseded updates: a server that gets or has installed a newer update no longer gets the one it replaces, so each ring switches as soon as the newer update is released there; once the newer update reached every ring the older one reached, the older rollout stops by itself (`Rollout.Superseded` in the audit log and the update timeline). The update list and the update page mark superseded updates.
- Start rules can test the restart behaviour Windows Update reports (no restart, may restart, restart required), and a rule with "no restart" can let its updates **install outside the maintenance windows** (delivered to the agent as `outsideWindows` only while the update is reported as never restarting). A new installation creates one such rule for definition updates once (all rings at once); `Rollout:CreateDefinitionRule = false` skips it. The update list shows the restart behaviour as a column with filter and grouping.
- Update page: "Progress by ring" shows when the rings the rollout has not reached yet can expect the update (from the minimum to the maximum waits of the transitions) and marks rings behind a manual gate.
- Server detail: administrators can **install the released updates now** ("Install updates now…"), with the restart right after or in the next maintenance window; only updates released for the ring of the server are installed.
- Server detail: a **Refresh** button, and the page refreshes itself every 10 seconds while the agent works or a remote action waits to be picked up or for its result (keeping the scroll position). - `POST /api/v1/agents/register`: issues client GUID and client secret, stores the client as `Pending`; rate limited per IP address.

- `GET /api/v1/trust/binding`: anchor-signed binding to the current TLS certificate; a new certificate gets the next serial on start.
- HTTPS only (default port 8443); TLS certificate from the Windows certificate store via `Trust:CertificateThumbprint`.

- `POST /api/v1/agents/inventory` (also before approval): stores client attributes, roles and installed updates, builds the update catalog from agent reports, logs changes of host name and domain; at most 5,000 updates and 4 MB per request.

- Maintenance windows on three levels (system default, group, server) maintained in the dashboard; the effective windows are delivered with the release list and increase its version when they change.
- Dashboard pages: Servers and server detail (Reader), Groups, Assignment rules and Maintenance windows (Admin); every change audited.
- Ring logic per update: start rules (classification, MSRC severity, title pattern; automatic with optional delay in hours, or manual) decide how a new update enters Pilot, by default every update starts automatically without delay; operators can start queued updates; transitions Pilot → Test → Production by minimum/maximum wait time, feedback rate and success rate (evaluated separately), manual gate (default on before Production), alarm on a poor success rate; gate approval, stop/resume and manual override to all rings; every action audited.
- Releases are derived from the rollout state: an approved server gets an update released for its ring that it reported as missing, until its inventory reports it installed; ring changes move releases.
- Dashboard pages: Updates (rollouts per ring and queued updates), ring transitions under Pending approvals, Administration → Release rules.
- Dashboard redesigned after the mockup (navigation sidebar, cards, charts drawn on the server as SVG, still without scripts; usable at phone width): overview with "Needs attention", key figures, deployment by ring and patch compliance trend (daily snapshot); ring detail page; server list with health and filters; server detail with pre-flight checks, missing updates and update history.
- Update detail page: progress per ring with rates, timeline, affected servers filterable by status, and rollout actions for operators.
- Reboot policy per system default, group and server ("Never" or "inside the maintenance window", default Never; among groups "Never" wins), delivered with the release list; server detail shows effective policy, last boot and whether a required reboot happened.
- Remote action queue: operators queue "search now", "full resync", "restart agent service" and "request agent logs" (ZIP of the last 3 days, at most 10 MB, stored with restricted access for 14 days, audited download), administrators "restart server" with confirmation, per server (audited, at most 10 open, cancellable until fetched, expiry after 24 h / 1 h); the heartbeat announces pending actions, `GET /api/v1/agents/actions` and `POST /api/v1/agents/actions/{id}/result` deliver and confirm them.
- Server time zone from the inventory (known IDs only); the server detail page shows the next maintenance window as a date.
- Coordinated groups with leases: share in percent with an upper bound (default 25 %, at most 5, at least 1), 2-hour leases, all-or-nothing across several coordinated groups, stop after failed or expired leases in a row (capped by group size), resume by operators, audited.
- AD coverage: enabled server accounts of the domain (Windows Server 2016 or newer only; older ones listed separately) compared with registered agents every 6 hours; coverage rate on the overview, page with servers without agent.
- User management for administrators (create, role, password, lock, delete; the last administrator is protected), server removal (delete keeping the history, delete with history) and clone detection (credentials used by two hosts in turn block the server until an operator decides).
- TLS certificate change in the dashboard (Admin, with confirmation): lists suitable certificates from LocalMachine\My, switches without restart and signs the next trust binding, so agents accept it automatically; audited.
- Windows Update error codes are translated into plain English text centrally.
- Notifications (Admin page): every minute new events are sent once, collected in one message, by e-mail (SMTP via MailKit, STARTTLS/TLS/relay) and/or a generic HTTPS webhook (JSON, optional HMAC-SHA256 signature, no redirects): servers waiting for approval, suspected clones, rollout alarms, gates waiting, stopped coordinated groups, expiring CA certificate and automatic certificate changes. Test button, audited changes; SMTP password and webhook secret DPAPI-protected outside the database and backup.
- Backup and restore: backup archive download in the dashboard (Admin, password of at least 16 characters; database online copy, trust anchor encrypted with PKCS#8/AES-256/PBKDF2, manifest; audited) and `SUSyphos.Server.exe restore <zip>` with the service stopped, validating the whole archive before replacing anything. The restored trust anchor is taken over by the service on its next start, so agents keep trusting a central server rebuilt on new hardware.
- Own TLS certificate: without a configured certificate the central server creates a self-signed one (RSA 3072, non-exportable machine key, 180 days) and rolls it over 30 days before expiry with a new key. Renewals of a CA certificate (autoenrollment or manual) are picked up every 15 minutes and at start, also after Windows archived the old certificate. A missing configured certificate falls back to the own one instead of stopping the service. Every change signs the next trust binding and is audited; lifetimes and interval under `Certificate:*`.

### Installers and CI

- The agent MSI no longer runs the validation ICE46, which sporadically failed release builds of unchanged commits.
- Browser tests of the dashboard (`tests/SUSyphos.UiTests`, Playwright with Microsoft Edge): every page in four window sizes against the layout rules, plus dialogs, filters and script features.

- MSI packages for agent and central server (WiX Toolset 7, self-contained publish, Windows Server 2016 or newer): Windows services under LocalSystem with restart on failure (agent also on error exit codes), options `SERVERURL` (agent) and `CERTTHUMBPRINT`/`HTTPSPORT` (central server, read from `HKLM\SOFTWARE\SUSyphos\Server`), firewall rule for the HTTPS port, upgrades keep options and data, data under ProgramData kept on uninstall. The central server service also starts without `CERTTHUMBPRINT` (own certificate); the CI install test covers that path.
- `build/Build-Installers.ps1` copies each MSI instead of keeping the hard link WiX creates to its intermediate file. Before, building 0.2.0 overwrote the 0.1.0 package of the upgrade test, so the CI "upgrade" only reinstalled the same package. The install test now checks that an upgrade replaces the product (new product code), also when started from a renamed file.
- Release files carry the version in their name (e.g. `SUSyphos.Server-0.3.0.msi`), so browsers do not rename repeated downloads; the CI install test upgrades from a renamed file and over a crashing old service.
- Central server MSI with installer interface (license, progress, final page with dashboard address, setup token note and "Open the dashboard") and a Start menu entry for the dashboard.
- Central server: startup errors are written to the log before the service ends; the expected SQLite migration warning is no longer logged.
- `build/Build-Installers.ps1` builds both MSIs; the GitHub Actions workflow builds and tests every push and installs, upgrades and uninstalls both MSIs on the runner (`build/Test-Installers.ps1`).

### Decided

- Supported from Windows Server 2016 on the latest .NET.
- Trust in the central server via a trust anchor with trust on first use and a local registry override; no runtime data in the client installer (`docs/03-communication-protocol.md`, section 3.2).
- Client secret issued at registration in addition to the GUID (`docs/03-communication-protocol.md`, section 3.1).
- All project artifacts (code, logs, documentation) are written in English.
- The agent reports no SID; rule-based approval will verify domain membership on the central server against AD and DNS.
- Central server address via registry, installer option `SERVERURL` and installer file name on download from the central server (`docs/03-communication-protocol.md`, section 3.3).
